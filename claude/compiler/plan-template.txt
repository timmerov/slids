SIDE-LOAD ONLY WHAT IS NEEDED
=============================

status:  LANDED 2026-10-21 — the PREREQUISITE and D, guard included (plan.txt INCOMPLETE
         TEMPLATES ARE INCOMPLETE CLASSES + THE SOURCE IS THE AUTHOR'S CALL). KEPT OPEN as a
         design record: the topic will be revisited — see AS LANDED and OPEN at the end.
         The sections in between are the design as DISCUSSED (2026-10-20/21); where they
         differ from what shipped, AS LANDED wins.
where:   today's behavior is documented in readme.txt (TEMPLATES, cross-TU: the three

GOAL
  A consumer loads a template source (t.sl beside t.slh) only when it needs that source's
  BODIES — i.e. only when it instantiates a flavor with a LOCAL argument (Tmpl<Priv>).
  Tmpl<int> and Tmpl<Public> never need it: their bodies come from t.sl's own
  --instantiate compile through the .sli demand pool.
  NEVER side-load unless the AUTHOR so indicates (D). The case this whole plan serves is a
  private class used as an argument to a public template.

BEFORE D (the state this plan started from; superseded 2026-10-21)
  lex::ImportWrapper::loadTemplateSource (lex.cpp) side-loads <dir>/<stem>.sl right after
  the header and its imports are processed, when ALL hold:
    1. the header declares a template (declaresTemplate: identifier + balanced <...> then
       `(` or `=`; lexical, errs toward loading)
    2. the .sl exists in the HEADER'S OWN directory (token::templateSourcePath)
    3. the .sl is not the root (token::samePath, by canonical path, never by stem)
    4. it was not already loaded (imported_once)
  It is marked template_source, opens its own privacy zone, and its imports are processed
  inside that zone.

  What a consumer does with it when every flavor is aggregated: lex, parse, register its
  template content (resolve strips everything else before relocation). Classify emits
  declaration-only instances; NO bodies from t.sl are code-generated in the consumer. The
  cost is the front end over t.sl and its imports.

  Where a local flavor is first KNOWN:
  - class templates: resolve, instantiateClassTemplate (inline_local = header_tmpl &&
    !here_sibling && anyArgLocal), reached from resolveTypeRef's template-use arm and the
    instance-qualified spelling arm. Which resolve pass gets there first depends on where
    the spelling appears: field/signature (1a-types / 1a), const/global init (1b), body
    local (2 / 2-scope), or only inside another instance's body (the
    pending_class_instances drain).
  - function templates: classify, instantiateTemplate, where the call deduces its args.
  Lex and grammar cannot know: they lack the symbol table (is Tmpl a template?), cannot see
  through aliases / nested args / qualification / deduction, and cannot ask the declaring
  file of the argument's class leaf (anyArgLocal peels pointers, iterators, arrays).

PREREQUISITE — AN INCOMPLETE TEMPLATE IS AN INCOMPLETE CLASS  (LANDED 2026-10-21; THE
  GUARD landed with D the same day)
  None of A/B/C/D works without this. An incomplete header template is no more special than
  an incomplete header class: OPAQUE to every importer, laid out only by its completer.
  The old "a template instance is NEVER OPAQUE" was an ARTIFACT of always side-loading the
  source — Vector<T>(...) gets its field list from the source's completing re-open, so
  every consumer happens to see it. Always side-loading is contrary to a major design
  goal; the artifact goes. Measured 2026-10-14 with loadTemplateSource gated off:
  Vector<float64> reports "declared incomplete ('...') and never completed" — that is
  the artifact surfacing, not a reason to keep the load.
  What it means, all of it the existing opaque-class machinery applied to flavors:
  - THE DISCRIMINATOR is the plain-class one: opaque everywhere except the completer. For
    an AGGREGATED flavor the completer is the --instantiate TU, which exports the flavor's
    __$sizeof word and __$ctor (anchored prefix) exactly as a plain opaque class's owner
    does. Aggregated flavors already have stable, suffix-free symbols, so every TU
    spells them alike. Opaque in EVERY consumer, including one that loads the source for
    some other (local) flavor — the flag must ride facts every TU computes alike.
  - An INLINE-LOCAL flavor is the template twin of a .sl-local incomplete class: only this
    TU can spell it, the source is loaded, it is laid out in place, never opaque.
  - A header template declared COMPLETE in the header (Box<T>) is untouched.
  - Consumers get opaque-class behavior: computed by-value embedding, sizeof a loaded
    word, runtime-sized globals on the heap, `new C[n]` via the heap slot. A consumer's
    aggregated clone STRIPS the source's fields (kept as source_private_fields for the
    private-field diagnostic), so `import` and `import+` consumers see one flavor.
  - Landed with it: LAYOUT WORDS + the main preamble (an owner whose hidden fields embed
    another module's size), and runtime layout retired (derived-from-opaque is computed).
  - THE GUARD (landed with D): an open header template in a consumer is not an error, any more than an
    open header class is. instantiateClassTemplate's cls_open check and the end-of-resolve
    sweep fire only where the completer should be. The canon negative Ngrow
    (test/import/tmpl_lib.slh) is then caught where a never-completed opaque class is —
    the owner's compile or the link — not in the consumer.

D. THE AUTHOR SAYS SO: import / import+  (chosen and LANDED 2026-10-21 — see AS LANDED)
  Syntax:
      import vector;       // the header only — never a side-load
      import+ vector;      // the header AND vector.sl, in its privacy zone as today
  `+` is an existing token and the next token after `import` is otherwise a path or `{`,
  so no lexer special case and no new reserved word. No `import-`: plain import already
  means "no side-load"; a third state needs a meaning first.

  Example:
      import vector;
      Priv() {}
      Vector<Priv> vec;    // ERROR: needs `import+ vector;`

  THE TWO ERRORS (no warnings, so both are errors — at least until warnings exist):
  - `import` where `import+` is required. Raised where inline_local is decided today:
    resolve (instantiateClassTemplate) for class templates, classify (deduction) for
    function templates. Falls out of the prerequisite: without the source a local flavor
    has no bodies to clone. Diagnostic shape: the private-name chain diagnostic's — primary
    at the use site, note at the local class, remedy note naming the `import+` line.
  - `import+` where `import` would do. Judged only after classify, once every
    instantiation has happened; skipped when an earlier error halted the pipeline (a halted
    compile never reached the statements that would have used it). NEEDED = some
    inline-local flavor drew on that source, or on a source it loaded transitively. Needs a
    per-source USED bit.
  Together they make the loaded set EXACTLY the needed set: deterministic, reproducible,
  no restart, no cache.

  TRANSITIVE LOADS — spec 2:
  - `import+ vector` loads vector.sl; every template header vector.sl imports has its
    source loaded too, recursively (template sources only). vector.sl's body using
    Helper<T> with T = Priv mints Helper<Priv> here, and helper.sl is already present.
  - Only the ROOT's own `import+` statements are judged by the unneeded error. Transitive
    loads never error.
  - Inside vector.sl, its own `import helper;` / `import+ helper;` is judged by
    vector.sl's OWN compile only (its own private classes). When main loads vector.sl,
    helper.sl comes along under spec 2 whichever spelling vector.sl used.
  - Cost: a transitive load can bring a source the flavor never uses. Front-end time only;
    the set is fixed by the import graph, so no effect on correctness or reproducibility.
  - FALLBACKS, if spec 2 does not hold up:
    1. no transitive load; main writes `import+ helper;` itself (though helper.slh is not
       otherwise visible to it) and the two errors cover it; the diagnostic names it.
    3. a template whose body mints another header template's flavor from T is unusable
       with a local argument.

  RULES:
  1. `import+` in a .slh is an error. A header's classes are all public, so it never mints
     a local flavor, and the load would be pushed onto every importer.
  2. `import+` on a header with no sibling .sl, or that declares no template, is an error
     (a case of "unneeded", with a message that says why).
  3. One file importing the same header both ways is an error.
  4. A source's own import spellings are judged by its own compile (see spec 2).
  5. No `import+` needed for: alias templates (type-level, delivered whole by the header);
     the injected provenance imports of an --instantiate compile (aggregated flavors only).
  6. A template COMPLETE in its header (Box<T>) still needs `import+` for a local flavor:
     its bodies are only in the source.

  BUILD:
  - `import+` is lexical, so the compile's -MF .d lists vector.sl exactly when it is
    loaded: an edit to vector.sl recompiles main only if main says `import+ vector`
    (given the prerequisite). The .d is still written right after lex.
  - --scan-deps keeps loading EVERY template source (A follow-up 3's last-but-one point):
    the library list and the library-to-library ordering edges come from t.sl's own
    imports. Its fragment keeps naming every scanned file, so editing t1.slh or t1.sl
    still re-scans main. A follow-up 4 describes the build unchanged.

  TESTS: every test using a local flavor today relies on the implicit load and gets the
  first error until it says `import+` — in test/import at least the Twin, Loc, tpock/tick
  and tbias cases.

A. RESTART WITH A KNOWN LIST  (SUPERSEDED by D, 2026-10-21)
  Kept as the record. Follow-ups 1-3 exist only to make an AUTOMATIC load cheap; D has no
  automatic load. Follow-up 4 still describes the build under D.
  - Pass 1 compiles WITHOUT side-loads. An instantiation that needs a source RECORDS which
    one and continues with a declaration-only stub, so nothing cascades. The stub is an
    OPAQUE flavor (the prerequisite's shape): layout queries go symbolic instead of
    erroring, so pass 1 reaches the end of classify — where function-template needs are
    found — instead of halting at a stage boundary.
  - End of classify: if the list is non-empty, discard pass 1 INCLUDING its diagnostics
    and re-run with "load the source beside <header>" for exactly those.
    Variant: class-template needs are known by the end of RESOLVE; restarting there when
    the list is already non-empty wastes less of pass 1, at the cost of possibly more
    iterations.
  - ITERATE: Tmpl<Priv2>'s body may use Helper<Priv2> from a header tmpl.sl imports — that
    need is only discoverable once that body exists. Re-run until nothing new is needed.
    Bounded by the number of template sources.
  - The request is attached to its HEADER, not a generic import, so it opens the privacy
    zone exactly as today's side-load does. lex::run's extra_imports is the nearest hook.
  - Deterministic: the final pass is an ordinary compile, so def_id numbering, symbols and
    the -MF deps all come from it.
  - Cost: a second front end, only for TUs that actually use a local flavor. No stage has
    to become incremental.
  - A local flavor is unspellable in any other TU, so A already compiles each one exactly
    once — the "once per instantiation" goal holds.

A FOLLOW-UP 1 — CACHE THE LIST
  - The cached list is a HINT; every compile validates it and restarts INTERNALLY (never a
    user-visible failed compile), then rewrites the cache.
  - TOO SHORT: always caught — pass 1 records every need it hits.
  - Detecting TOO LONG needs a USED bit per loaded source (did any inline-local flavor
    draw on it), not only the record of needed-but-unloaded sources.
  - TOO LONG: compiles correctly (extra source stripped, names private to its zone), costs
    only load time — BUT import order changes def_id numbering, so suffixed local symbols
    shift and the .o differs from an exact-set build.
    For reproducible builds: loaded set != needed set restarts once with the EXACT set, so
    the output depends only on what is needed. Costs one extra pass when the set shrinks.
  - Clean build: two passes for every TU using a local flavor; steady state: one.

A FOLLOW-UP 2 — A CHEAP PRE-SCAN (precision ladder)
  No exact cheap scan exists. Rungs:
  1. the root declares NO class of its own (nested and function-local count): no local
     flavor is possible, load nothing. EXACT. Probably most TUs. Detectable lexically or
     by a grammar-only parse of the root (unverified whether grammar's decl recognizers
     need anything from imports).
     Exact only while "local" means what resolve's firstLocalArg says: a root-declared
     class leaf, peeled through pointers / iterators / arrays. It does NOT peel tuples, so
     Box<(Loc, int)> would read as aggregated (from reading, unverified — a possible
     latent bug outside this plan).
  2. classes exist: load a template's source if the root mentions that template's name at
     all. OVER-APPROXIMATE.
  3. anything sharper is pass 1. A scan cannot see: deduced calls (foo(priv) has no <...>),
     aliases (alias P = Priv; Tmpl<P>), needs inside a loaded source (tmpl.sl's
     Helper<T>).
  Rungs 1 and 2 would fit in --scan-deps or the front of lex.
  Combined roles: restart = correctness backstop; cache = steady state; rung 1 =
  clean-build shortcut. Rung 2 adds little once the cache exists and, under the exact-set
  rule, would force restarts whenever it over-loads.

A FOLLOW-UP 3 — THE CACHE LIVES IN THE MAKE DEPENDENCY FILE
  - The compile writes the list into its .d (-MF) as a TARGET-SPECIFIC variable — the
    pattern --scan-deps already uses for SLIDS_INST (main.cpp):
      build/main.ll: main.sl lib/hdr/t.slh lib/hdr/t.sl ...
      build/main.ll: SLIDS_SIDELOAD = --side-load lib/hdr/t.sl
  - The .ll rule passes it back beside $(SLIDS_INST) (lib/Makefile's .ll rule); the .d is
    already pulled in by `-include $(wildcard $(BUILD_DIR)/*.d)`.
  - The compiler stays stateless; make carries the cache. No .d yet: empty list, internal
    restart. Stale: internal restart. Final pass writes the correct .d.
  - The .d's FILE LIST stays right as-is (-MF writes tokens.files): if main loaded t.sl an
    edit to t.sl rebuilds main; if it did not, it never depended on t.sl (given the
    prerequisite).
  - CHANGE: today the .d is written right after lex so it survives a later error; under A
    it is written after the FINAL pass's lex.
  - The .d, not the .deps.mk: --scan-deps is lex-only and cannot compute the exact list.
  - --scan-deps must KEEP loading every template source: its library list (SLIDS_INST,
    <consumer>_TMPL_OBJS) comes from f.template_source, and the library-to-library
    ordering edges come from t.sl's OWN imports. Only the COMPILE's loads become
    conditional. Cheap: the scan is lex-only.
  - A manual compile without -MF has no cache and always pays the restart.

A FOLLOW-UP 4 — HOW OFTEN --scan-deps RUNS (unchanged by this plan)
  - Once per TU on a clean build.
  - Again when its rule's prerequisites change: the TU's .sl or the SLIDSC binary
    (`<bld>/<name>.deps.mk: <name>.sl $(SLIDSC)`).
  - Again when any file in its scanned closure changes: the fragment names itself as
    depending on every file lex opened (`<fragment>: <every scanned file>`) — headers,
    side-loaded sources, their imports.
  - Mechanism: make's remake-the-makefiles — the -include'd fragment is remade, then make
    RE-EXECS and re-reads its Makefiles. Skipped for `make clean`.
  - Users: lib/ (LIB_SRCS) and ten test dirs (expression, pointer, misc, flow, assign,
    template, function, guthrie, lib, progress).
  - In practice: editing one test .sl = one cheap scan; rebuilding the compiler = every
    fragment rescans plus a re-exec per directory; editing a library header or template
    source = rescans its importers.

B. CATCH UP AFTER CLASSIFY  (not recommended)
  - At the end of classify, side-load only the needed sources and run lex..classify over
    just the new content into the already-processed tree.
  - The stages are whole-program by design: resolve's ~13 ordered sweeps (names before
    types before signatures before bodies), constfold's fixpoint, classify's signature
    pre-pass before any body.
  - There IS precedent for late INSTANCES (the pending_class_instances drain,
    constfold::runOn, classify's on-demand instantiation) — but not for late SOURCES.
  - A late source can COMPLETE a template whose flavors are already laid out, and its
    template functions can JOIN overload sets that earlier calls already resolved — the
    result would depend on load timing.
  - The source's own imports are general headers; any not already loaded need EVERY pass.
  - The payoff over A is only pass 1's front end.

C. SEPARATE INSTANTIATION TU + INTERNALIZE  (the todo.txt design)
  - At end of file, treat Priv's flavors as public: write the demand to the inst file,
    compile it with main.sl loaded as if it were a header, merge, and make the now-public
    Priv symbols private again in main_inst.o.
  - Loading main.sl as a header needs a NEW STRIP MODE (bodies, globals, main dropped;
    types kept) — the template-source strip in the other direction.
  - SYMBOL IDENTITY: file-scope private classes carry no def_id suffix (canon Twin), so
    they match across the two compiles; nested / function-local classes carry a def_id
    suffix and def_id depends on import order — they need TU-stable naming first.
  - Tmpl<Priv>'s bodies call Priv's methods, internal to main today, so main must EXPORT
    them and they must be hidden again after the merge: llvm-link + `opt
    -passes=internalize` + api-list. The 2026-10-14 spike failed (llvm-link dropped an
    internal def a declare needed, exit 0) and was rolled back.
  - Build: --scan-deps is lex-only, so it cannot tell which TUs need a main_inst.o; the
    make rules must produce one always or conditionally.
  - Payoff: main's compile never sees a template body. Small — A already compiles each
    local flavor exactly once.

RECOMMENDATION
  1. The prerequisite: incomplete header templates become opaque like incomplete header
     classes; aggregated flavors export their layout from the --instantiate TU.
  2. D: `import` / `import+`, both errors, spec 2 for transitive loads (fall back to 1,
     then 3).
  3. A superseded. C only if main must never contain template bodies. B no.

      missing:  primary at the IMPORT STATEMENT — "A template declared in 'vector.slh' is

  - THE CHAINING RULE (user, at the go): the header DECLARING the instantiated template is
    the one to `import+`. main importing a.slh and instantiating Vector<Priv> writes
    `import+ vector;`; instantiating A<Priv>, `import+ a;`. When the instantiating file has
    no statement for that header, the missing error's primary is the instantiation itself.
  - SPEC 2 held: makeFull loads the header's source, then recurses over the import
    statements of the header AND of its source (each in its own privacy zone). It also
    recurses into the header's plain header imports — slightly wider than "template headers
    vector.sl imports", still fixed by the import graph.
  - WHERE: missing — resolve requirePrivateInstanceSource, from instantiateClassTemplate and
    instantiateTemplate (functions AND template methods share it; classify reaches it
    through instantiateTemplate). USED bit — Tree.header_source_used, set there. Unneeded —
    main.cpp right after classify. Lexical rules — lex, reported after parking.
  - NEW MACHINERY D did not foresee: the lexer CONSUMES import statements, so a diagnostic
    had nothing to point at. Each statement is a token::ImportStmt and its `import` token is
    PARKED past kEndOfInput; grammar's `>>` split had to shift parked indices.
  - THE NEGATIVE RUNNER: a `.slh` case now also compiles the header's sibling `.sl` (where a
    template header's own completion is judged); Ngrow passes there.
  - SWEEP: test/template tmpl_complete.sl; test/import tmpl_test, tmpl_test2, bird;
    test/guthrie guthrie.sl and electorate.sl (chaining — `import+ vector` added beside

  - All other suites pass unchanged.
